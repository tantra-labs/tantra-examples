# 0004 — Data-Provisioning Microservice: Scope (download / dummy / Monte-Carlo)

**Status**: Proposed — scoping only, **no implementation** (2026-11-16).

**Decision (2026-11-16)**: a provisioning **microservice** serves example data
options (download real / populate dummy / Monte-Carlo randomized) instead of
another CLI. Interactive choice is surfaced to users through the service, not
through a per-repo `provision` command.

## Problem

The examples, screeners and backtests need a market-data lakehouse (1D NSE price
catalog, fundamentals, mutual-fund data) that the workspace does not ship. Today the
gap is papered over two ways, both with drawbacks:

1. **Offline seam (`VYAAPAAR_DATA_DIR`) + per-test synthetic fixtures** —
   `tests/unit/synthetic_lakehouse.py` and the `_synthetic_catalog` helpers generate
   deterministic parquet/duckdb roots. There is no one canonical generator, the
   generators are test-side, and a user of the examples has no way to *choose*
   between real data, dummy data, or randomized data from the command line or a notebook.
2. **Silent fallback / skip** — catalog-gated tests `skip` with an offline-seam message,
   and `load_real_bars` falls back to a straight-line ramp with no user-facing choice.

A user asked to run the examples against real data has no supported path: the real
catalog must be built by hand from the tantra-data ingest CLIs, and there is no
interactive "download it, populate dummy data, or generate Monte-Carlo data" choice.

## Scope of the service

A small HTTP microservice (the owning component for example data provisioning) that
**provisions a data root** (the `$VYAAPAAR_DATA_DIR` layout) on request. It is the single
canonical source of synthetic lakehouse data and the supported route to real data.

### Datasets the service can provision

| Dataset | Layout produced | Mode support |
| :--- | :--- | :--- |
| `nse_1d_catalog` | `<root>/catalog/1D/NSE/<SYMBOL>/<year>.parquet` (ts ns + OHLCV) | download, dummy, monte-carlo |
| `fundamentals` | `<root>/fundamentals.duckdb` (`companies`, `financial_ratios`, `financial_statements`) | download, dummy, monte-carlo |
| `mutual_funds` | `<root>/mutual_funds.duckdb` (NAV + holdings, per `tantra_data.store.mutual_funds`) | download, dummy, monte-carlo |

### Provision modes

1. **`download`** — real data. Delegates to the owning ingesters:
   `tantra_data.cli.ingest_catalog` (NSE bhavcopy backfill), `ingest_fundamentals`
   (yfinance), `ingest_mutual_funds` (AMFI NAV). Requires network + vendor availability;
   long-running → the microservice runs it as a background job with progress/status.
2. **`dummy`** — deterministic synthetic lakehouse. This is the fold of the current
   test fixture `tests/unit/synthetic_lakehouse.py` (same layout, same values) lifted
   into the service so there is exactly **one** synthetic-data implementation. Idempotent:
   same request → same root.
3. **`monte-carlo`** — randomized price/fundamentals series generated by a seeded
   GBM-style model (geometric Brownian motion with configurable drift/vol, or a
   regime-switching model) over the chosen symbol set + calendar window. **Truly random
   unless a `seed` is supplied**; with a `seed` the run is byte-identical (fits the
   research-live parity / replayability rules and makes randomized backtests
   reproducible). Useful for strategy/backtest robustness work.

### Request / response contract (illustrative)

```
POST /provision
{
  "dataset": "nse_1d_catalog",          // nse_1d_catalog | fundamentals | mutual_funds
  "mode": "monte-carlo",                // download | dummy | monte-carlo
  "seed": null,                          // null → truly random; int → reproducible
  "symbols": ["RELIANCE", "TCS", ...],   // optional; default = the example universe
  "start": "2020-01-01", "end": "2025-12-31",
  "data_root": null                      // null → $VYAAPAAR_DATA_DIR or the default root
}
→ 202 Accepted { "job_id": "...", "status": "running" }
GET /provision/jobs/{job_id} → { "status": "done", "written": {...}, "root": "..." }
```

- Idempotent: re-provisioning the same dataset+mode into an existing root either skips
  (when the layout is already present and complete) or rebuilds when `force=true`.
- All financial values written by the service are exact `Decimal` (zero-floats policy):
  parquet OHLCV and duckdb ratio/statement columns keep the decimal128 / DECIMAL
  schemas the tantra-data bridge uses.
- The service never fabricates data it cannot: `download` failures (no network, vendor
  down) surface as a terminal job error, not silent empty data.

### Why a microservice rather than a CLI

- Long-running ingestion (the real catalog is hundreds of MB) needs background jobs,
  progress, and cancellation — a natural service concern, not a CLI's.
- The examples are used from notebooks, other machines and remote runners; a service
  serves the same data root to many clients without re-running ingestion per process.
- A CLI would duplicate the tantra-data ingest entry points; the service is the thin
  orchestration layer over them, keeping one provisioning path.
- The interactive "which option?" choice the user asked for is surfaced by a tiny client
  (or the examples' runtime seam) that calls the service; the service itself is
  non-interactive HTTP.

## Interaction with existing seams

- **Data-root resolution is unchanged**: everything already reads through
  `tantra.store.find_data_root` / `tantra_examples.screening.paths`
  (`find_catalog_path`, `find_duckdb_path`, `find_mutual_funds_db_path`), all honoring
  `$VYAAPAAR_DATA_DIR`. The service just *writes* the canonical layout; consumers are
  untouched.
- **Test wiring (one canonical source)**: `tests/unit/synthetic_lakehouse.py` is folded
  into the service's `dummy` mode. The unit tests call the provisioner's in-process
  dummy generator (or, in integration, the service) instead of owning their own
  generator. This makes the ad-hoc per-test `_synthetic_catalog`/`_write_symbol_parquet`
  helpers redundant over time.
- **Per-example runtime prompt (future)**: when an example finds an absent data root,
  it may surface the service's three options (download / dummy / Monte-Carlo) and
  invoke the chosen one — the choice the user asked for, without a new CLI.

## Milestones (draft build order — NOT started)

1. **Contract + layout** — OpenAPI spec for `/provision`, job status, canonical layout
   constants; a `provision` library package with the three generators as pure functions
   (dummy first — the fold of `synthetic_lakehouse.py`).
2. **Dummy mode** — the canonical deterministic lakehouse; tests re-pointed to it.
3. **Monte-Carlo mode** — seeded (or truly-random) GBM/regime generator + fundamentals
   randomizer; golden/seed vectors for determinism tests.
4. **Download mode** — job runner over `tantra_data.cli.ingest_*` + provider failures
   surfaced as terminal errors.
5. **HTTP service** — background job store, progress, cancellation; thin client.
6. **Example seam** — runtime prompt wiring; remove redundant per-test generators.

## Dependencies / blockers

- **`tantra_data.store.mutual_funds` does not exist yet** (filed as
  `tantra-data/docs/gaps/0023-*.md`). The `mutual_funds` dataset's *consumer*
  (`screen_mutual_funds`) cannot run until the provider ships that store surface; the
  service may still provision the duckdb layout once it is specified.
- Download mode needs network access and the live vendors (NSE bhavcopy, yfinance,
  AMFI) — the same live sources the tantra-data ingest CLIs already use.
- Storage: a full real catalog is large; the service should stream/write
  year-partitioned parquet and report disk usage in job status.

## Non-goals (for now)

- **No implementation in this scope** (decision 2026-11-16).
- No new CLI surface in tantra-examples.
- No change to `VYAAPAAR_DATA_DIR` resolution semantics.
